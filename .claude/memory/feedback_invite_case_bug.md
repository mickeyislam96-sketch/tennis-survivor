---
name: Invite-link case-sensitivity class of bug
description: Generation/lookup must agree on casing — never use Date.now().toString(36) (lowercase) for a code that's looked up via .toUpperCase() comparison
type: feedback
---

When the same field is touched by two code paths (generation AND lookup),
force-pin them to the same casing or use a case-insensitive comparison
from day one.

**Why:** On 5 May 2026 we shipped Rome 2026 with invite code generation
that produced mixed-case codes (`groupName.toUpperCase() + Date.now().toString(36).slice(-6)`)
because `Date.now().toString(36)` returns lowercase. The lookup endpoint
uppercased the URL parameter and ran case-sensitive `WHERE invite_code = $1`.
Result: every invite link to Rome 404'd silently. Roughly half of all
historical pools had latent versions of the same bug — Madrid only worked
because its code happened to be regenerated by the admin endpoint
(`Math.random().toString(36).slice(2,8).toUpperCase()`).

**How to apply:**
- Any time you generate a code that will be looked up by URL or email,
  the generation function and the lookup function must be tested
  together in the same commit.
- Prefer `WHERE UPPER(col) = UPPER($1)` (or LOWER) over relying on
  generation discipline alone — defence in depth.
- The smoke test (`scripts/smoke.sh`) now round-trips the active pool's
  invite code in both stored and uppercased forms. Keep that step.
- Same lesson applies to: tournament IDs (kebab-case lock-in), user
  display names (trim + normalise), email addresses (lowercase store),
  Stripe customer IDs (case-sensitive — never normalise).
